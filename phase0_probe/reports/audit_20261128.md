**Arcus 重连、心跳、resync 的隐患：**
- **竞态：基本没有。** 每个 feed 是单个 task，handle 全同步（feeds.py:93,95-131），ArcusSync 的 buffer、book 只在同一协程里改，所以不存在并发 resync。
- **重连风暴（P1）：** `run()` 在出错后固定 `sleep(1)` 再连，次数无上限（feeds.py:77-78）。持续出现 mid-stream gap 时，单个 feed 每分钟会新建大约 60 条连接，已经超过 Arcus 的 50/min/IP（api-reference_rate-limits.md:158）。7 个 feed 共用一个 IP，问题会放大。HL 同理（210-211 行对比 30/min）。ArcusMarketsFeed 也一样（161-162 行）。
- **baseline_gap_resync 活锁（P2）：** `ArcusSync.on_delta` 在 provisional 状态下遇到跳号时，会 `invalidate` 并把 buffer 重置为这一条 delta（book.py:187-193），然后等下一帧 `l2Orderbook` 重建。如果每次快照后的首个 delta 都跳号，就会无限循环 provisional→invalid，**不重连、没有计数上限、不告警**（feeds.py:117-120 只写 event，`baseline_gaps` 无界）。这不会占满 CPU，但该标的会长期 NOT_READY。
- **增量流静默停滞检测不到（P1）：** 如果 `l2OrderbookUpdates` 停止推送，而 `l2Orderbook` 照常推送，`arcus_heartbeat` 会一直返回 `"behind"`（book.py:239-240），book 不会失效。同时每帧心跳都会刷新 `latency_ms`（book.py:235-236），`last_msg_ms` 也被刷新（feeds.py:97），所以 `model.evaluate` 的 stale 门控（model.py:178-181）**不会触发**。结果是旧盘口被当成 `ok` 参与定价。`confirmed_ms`/`age_ms` 能看出停滞，但从 PR #1.5 起只作诊断（book.py:71-73），不参与门控。
- **`ahead` 分支：** 返回后什么也不做（feeds.py:125-131），合理。
- **心跳校验只比前缀（P2）：** `k = min(len(hb), len(book))`（book.py:244）。本地档位少于 20 时只比较较短的前缀。另外本地保留 100 档，校验只覆盖前 20 档，VWAP 却会走到 21–100 档，这部分没有被校验。
- **degraded 帧不处理（P2）：** 进入 NOT_READY 本身是安全的，但不会记 event。
- **task 取消：** 退出时 `stop.set()` 后 `asyncio.wait(tasks, timeout=10)`（record_spreads.py:130），没有显式 cancel，剩下的交给 `asyncio.run` 收尾。由于 store.close 之后没有 await 点，不会写已关闭的 DB，这一点可以接受。**真正的问题是运行中 task 崩溃没人察觉**：`tasks` 列表从头到尾没有被 await 或检查结果（record_spreads.py:122-127）。
- **websockets 17.4：** `asyncio.wait_for(ws.recv(), 1)`（90、155、228 行）取消 recv 在新版 asyncio 实现里是安全的【依据官方文档，本次未专门验证】。

**Arcus 部分：**

### 3. model.py 和 realism.py：300 s 中枢滞后、trades.side 假设边界、touch/through 边界

**300 s 滚动中枢的滞后：**
- 实现：`RollingMedian`（model.py:125-146），窗口 300 s，至少 30 个样本，严格只用 `t < now`（138 行），没有未来函数（已有测试 test_model.py:225）。
- 推入条件：两侧 book 都 fresh（recorder.py:59-62）。
- **滞后特性：** 中位数在基差发生阶跃后，大约要等新状态的样本超过窗口的一半（约 150 s）才会切换。这段时间里 `net_resid = net ∓ 旧中枢`（model.py:219-221），开盘时基差剧烈跳变，会**在约 2.5 分钟内系统性地产生假机会，或掩盖真机会**。另外，开盘前如果有 NOT_READY 时段，样本会断档，min_samples=30 会造成约 30 s 预热（`warmup_seconds`，analysis.py:93）。
- 建议：只做离线分析参数，不动录制。在 analyze 里加入开盘后 N 分钟的剔除和对照，或者加一个更短窗口（如 60 s）的对照列。

**trades.side 吃单方向假设的边界：**
- 假设：Arcus `side` 是 taker 方向（trades.py:9-12,32），HL 的 `B/A` 是 aggressor 方向（16-18,31）。两者都标了 `TODO: VERIFY_FROM_DOCS`。
- **关键事实：** 穿价过滤 `fill_evidence` **只用成交价，不用 side**（`load_trades` 只查 `price`，realism.py:114-116）。所以 side 假设错了也**不会**影响过滤结果，只影响 `side_consistency` 诊断（realism.py:215-239）和 trades 表的 `side` 列。
- 边界情况 1：Maker BUY 遇到“价格 ≤ P 的买方吃单成交”，只有在卖一已经 ≤ P 时才会出现，此时我们的单本来也会成交，可以算良性。
- 边界情况 2：HL 订阅时会回放 30 笔成交（trades.py:19-21），靠 UNIQUE 约束去重（store.py:32），回放的成交按交易所时间被窗口排除。
- 边界情况 3：`side_consistency` 用 `ts_us // 1000 // 1000 * 1000` 对齐到秒（realism.py:226），而 1 Hz 的 mid 是在整秒稍后采样的，存在亚秒级错位，诊断精度有限。

**touch 和 through 过滤：**
- `crosses`（realism.py:52-55）：touch 用 `<=` / `>=`，through 用 `<` / `>`，**和文档描述一致，没有写反**。
- 窗口是 `(t, t+W]`：`bisect_right(t)` 排除恰好落在 t 的成交，`ts > t+W` 时 break，所以包含 t+W（realism.py:64-73）。
- 误判倾向：
  - touch 模式偏乐观：等价成交时排队位置未知（文档也承认）。
  - through 模式偏保守：P 档只被吃掉一部分时会被误杀。
  - 样本时间戳 `nxt` 是整秒，但盘口实际在 `nxt + δ` 才读到，δ 内发生的成交会被算作证据，带来轻微的乐观偏差，可以忽略。
  - 成交时间是**交易所时钟**，t 是**本地时钟**，Arcus 的 clock offset 测了（record_spreads.py:93-97）却没用在成交时间上，所以窗口边界有几十到几百 ms 的错位【估算】。
- **book 证据回退**（realism.py:70-76）只用 `ready=1` 的盘口顶（120-128）。窗口内如果出现 NOT_READY，就会缺证据，导致**误杀**。
- **trades 表缺失时的回退存在缺陷（P2）：** `store.SCHEMA` 总会创建 trades 表（store.py:29-33），所以对新库来说 `has_trades_table`（realism.py:106-107）**永远为 True**。没加 `--record-trades` 录的库，报告会显示 “Trades table present … 0 trades”，而“No trades table”的提示（analyze_opportunity.py:76-79）只对旧库生效。`meta.record_trades`（record_spreads.py:100）已经写了，却没有使用。
- **逆向选择口径混用（P2）：** p0 是对冲腿的 VWAP（opportunities 行），t+k 时如果该行不是 ok，p1 会回退到**盘口顶**（realism.py:187-191）。对冲 SELL 时 VWAP ≤ best bid，回退会把逆向选择**系统性低估**；报告里有 `top_of_book_fallback` 计数，可以据此甄别。

### 4. store.py 和 recorder.py：SQLite 模式、提交方式、阻塞与磁盘

| 项 | 实测结论 |
|---|---|
| WAL | **没有开**。`sqlite3.connect(path)`（store.py:43）没有设置任何 PRAGMA；现有 4 个库的实测 `journal_mode=delete` |
| synchronous | 默认 FULL（未设置） |
| 提交方式 | **按秒批量**：opportunities 和 book_health 用 `executemany`，每秒在 `Recorder.sample` 末尾 commit 一次（recorder.py:67-78）；funding 每 5 秒一批（69-77）；trades 在每个 WS 帧里调用 `executemany` 但不 commit，跟着下一次 1 Hz 一起提交（store.py:65-72，record_spreads.py:103-105）；events 逐条 `execute`（store.py:74-75）；`put_meta` 立即 commit（47-48） |
| 是否阻塞事件循环 | **是**。所有 sqlite 调用都在事件循环线程里同步执行，没有 executor 或线程 |
| `sample()` 耗时 | 【实测，合成数据，7 对 × 3 Q × 6 组合 = 126 行/秒，本机 /tmp】p50 3.8 ms、p90 8.0 ms、max 25.4 ms。VPS 磁盘的 fsync 更慢，【估算】可能到 10–50 ms，相对 500 ms 的 latency 门限可以接受 |
| 锁表 | **会**。rollback journal 模式下，读方持有 SHARED 锁会阻塞写方 commit；默认 busy timeout 是 5 s。录制期间如果对同一个库跑 `analyze_opportunity.py`（summarize 要遍历全表，几百 MB 的库可能超过 5 s），`sample()` 里的 `commit`（recorder.py:78）会抛 `sqlite3.OperationalError: database is locked`，**sampler task 会静默死亡**（recorder.py:93-102 没有兜底），之后整场录制不再落盘，进程却继续运行 |
| 写入量 | 每秒 opportunities 126 行 + book_health 14 行；funding 每 5 秒 14 行；trades【估算】RTH 每个标的每秒约 0.3–5 笔（现有 trades_live_check 是非 RTH 时段：HL NVDA 61 笔/120 s，其中 30 笔是回放；Arcus NVDA 35 笔/120 s）【RTH 实际值未验证，周五的 RTH 数据不在仓库里】 |
| 磁盘增长 | 【实测基准】`rwa_connectivity_10m.sqlite`（5 对，600 s）为 33.5 MB，dbstat 显示 opportunities 30.5 MB，ix_opp 2.5 MB。**【估算】7 对 × 2 h ≈ 33.5 MB ÷ 10 min ÷ 5 对 × 7 对 × 120 min ≈ 0.56 GB**，加上 trades（每行约 160–200 B 含索引，最多约 10–20 MB）。**结论：大约 0.6 GB，可控但不算小**，VPS 建议至少留 2 GB 空闲。DELETE 模式每次提交还会创建和删除一次 `-journal` 文件 |
| 中断安全 | rollback journal 能保证一致性，最多丢最后约 1 s 未提交的数据；tmux 被 kill（SIGHUP）不会走 finally，`ended_ms` 和 stats meta 会缺失 |

### 6. 架构解耦度：接入 RiskEngine、10 态 OrderStateMachine、PaperTradingEngine 前必须先拆的边界

1. **Feed 同时承担传输、协议和状态**（feeds.py:48-138、182-265）：连接、订阅、解析、book、funding、stats 都在一个类里。**必须拆成** Connection 层、Decoder 层，以及通过事件总线发布 `BookUpdated / TradeEvent / FundingUpdated` 的 MarketDataBus。Recorder、Strategy、Risk、Paper 都作为订阅者。这一步也是 HL 多路复用的前提。
2. **Recorder 是“上帝对象”**（recorder.py:30-102）：它直接读取 Feed 内部的 book（55、64-66）、调用 evaluate、维护 RollingMedian、轮询 HL REST、写 Store。必须拆出 `BasisTracker`（RollingMedian 和推入策略）和 `Sampler`（只负责采样和持久化）。信号产出改为发布 `Signal`，再由 Risk 消费。
3. **定价和门控混在一起**：`model.evaluate` 内部判断 ready/latency/silence（model.py:176-181），直接依赖 `OrderBook` 的可变内部字段。RiskEngine 需要独立的数据质量和风控门，应把门控上移，evaluate 只接收不可变的 `BookView` 快照，也方便 Paper 回放。
4. **持久层反向依赖领域层**：store.py:8-9 导入 `Opportunity` 和 `Trade`；analysis.py 和 realism.py 直接写 SQL 读 schema（analysis.py:44-46、realism.py:114-145）。接入 OMS 或 Paper 之前需要 Repository 接口和 schema 版本号（meta 里加 `schema_version`）。另外 SQLite 同步写需要改成异步写队列，否则订单事件的延迟会受磁盘影响。
5. **全局时钟**：`dec.now_ms()` 在 feeds、recorder、record_spreads 里被直接调用（feeds.py:93,158,222-231；recorder.py:45,95）。OrderStateMachine 的超时状态和 Paper 回放都需要注入 `Clock`，否则不可测，也无法确定性回放。
6. **状态和枚举是自由字符串**：`Opportunity.status`（"ok"/"stale"…，model.py:90）、sink 的 `kind`（feeds.py:22）、realism 的 `MAKER_MODES` 字符串（realism.py:28）。10 态状态机需要强类型 Enum 和合法转移表，应新开模块，不要复用这些字符串。
7. **Paper 的数据瓶颈**：DB 里只有 1 Hz 盘口顶（book_health）和固定 Q 的 VWAP（opportunities），没有完整 L2。所以 PaperTradingEngine **无法基于现有录制做任意 Q 的回放**，只能接实时 BookView，或者以后加 L2 增量录制（会带来明显的磁盘成本）。`realism.crosses / fill_evidence`（52-77）是纯函数，**可以直接作为 Paper 的成交判定内核复用**。
8. **静态守卫的影响**：`test_read_only_no_signing_keys_or_order_endpoints`（test_discovery_and_static.py:132-139）扫描 src 和 scripts 全部文件（CODE 定义在第 20 行）。在用户解除约束之前，OMS 和执行代码**不能**放进本包。即使只是纯模拟的 OrderStateMachine 或 Paper，也建议放在独立包里，并先征得用户对阶段约束的确认。

### 1. 最亟需解决的 Top 5 技术问题
| 级别 | 问题 | 位置 |
|---|---|---|
| **P0** | **任何 task 未捕获的异常都会静默死亡，且没有监督**：feed 只捕获几类特定异常，`ValueError/KeyError/zlib.error` 会穿透；sampler 完全没有兜底；`tasks` 列表从不检查结果。周一录制可能悄悄丢掉一个标的，甚至整个落盘，进程却照常跑完 | record_spreads.py:122-130；feeds.py:62-78、148-162、198-211；recorder.py:93-102；trades.py:56,69；book.py:257,284；feeds.py:179 |

### 2. Sprint 2 最应该先动的 3 个文件和最小改动方案
**兼容性红线：** `record_spreads.py` 的 CLI 参数和 DB schema（5 张表 + meta 及其列）**都不变**，新增内容只限于 events 的新 `kind` 值和新的 meta 键。HL 多路复用和架构拆分**放到周一录制之后**。

1. **`scripts/record_spreads.py`（task 监督，对应 P0）**
   - 新增一个 `_supervise(name, factory)` 协程：`while not stop` 循环里 `try: await factory()`，捕获 `except Exception` 后写 `rec.sink(..., "task_crash", repr(exc))`，invalidate 对应的 book，退避后重启。
   - 用它包住 feed、sampler、poll_predicted 的 task 创建（122-125 行）。
   - 结束时对 `tasks` 收集 `exception()` 并写入 meta。
   - 加上 SIGTERM/SIGHUP 处理，触发 `stop.set()`，保证 tmux 被关闭时也会写 `ended_ms` 和 stats。
   - CLI 不变。
2. **`src/phase0_probe/store.py`（对应 P1：锁和阻塞）**
   - 在 `__init__` 里改成 `sqlite3.connect(path, timeout=30)`，然后执行 `PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;`。
   - `close()` 时先 `PRAGMA wal_checkpoint(TRUNCATE)`，再关闭。
   - schema 完全不变，旧库可以直接打开。
   - 注意：WAL 会产生 `-wal/-shm` 文件，拷贝库要么在 close 之后拷，要么三个文件一起拷。
   - 同时在 `recorder.sample` 的 commit 外层捕获 `sqlite3.OperationalError`，写 event 后跳过这一秒，不让 sampler 死掉（只需改 recorder.py:78 一行附近）。
3. **`src/phase0_probe/feeds.py`（对应 P1：重连和停滞）**
   - (a) 三个 `run()` 改成指数退避加抖动（1→2→4…最多 30 s，连接稳定 60 s 后复位），保证每个 IP 每分钟新建连接远低于 30。
   - (b) `except` 增加兜底 `(ValueError, KeyError, TypeError, zlib.error)`，写 `parse_error_reconnect` event。
   - (c) HL 加 pong 看门狗：`now - last_msg_ms > 15 s` 时 raise TimeoutError 触发重连。
   - (d) Arcus 在 `handle` 里统计连续 `behind` 次数：超过 N 次（如 25 次，约 5 s）并且 `seq` 一直在前进时，raise `BookIntegrityError("delta stream stalled")` 重建盘口。
   - 以上都不改接口，`HlBookFeed/ArcusBookFeed` 的构造签名和 `handle` 语义保持不变，现有 143 个测试应该不受影响。
   - 每项各配一个单元测试（用假 ws 或直接调用 handle）。
